# LLM 상태 표시와 작업별 토큰 사용량 설계

- 작성일: 2026-11-07
- 시안: [mockups/llm-status.html](mockups/llm-status.html)
- 표기: **[결정]** 은 사용자가 정한 것, **[제안]** 은 설계자가 정한 것, **[빌더]** 는 구현자 재량.

## 1. 왜

사용자는 상태 표시줄 오른쪽 아래를 보고 두 가지를 알고 싶어 한다.
- 지금 LLM과 통신 중인지, 입력을 보내는 중인지 답을 받는 중인지
- 이 영화(프로젝트)를 처리하면서 어느 작업에 토큰을 얼마나 썼는지

OpenAI API로 바꾸면서 쓴 양을 알고 싶어졌다. 그전에는 교정이 0%에서 멈췄을 때 무슨 일이 일어나는지 볼 수단도 없었다.

**비목표:** 작업별로 다른 모델 고르기 **[결정]**, 금액 표시 **[결정]**(가격표를 직접 넣거나 내장해야 해서 뺐다), 요청·응답 원문 로그.

## 2. 상태 표시줄 [결정]

- 오른쪽 끝에 역할 두 개를 늘 같은 라벨로 보여준다. 작업 이름으로 바꾸지 않는다.
  - `● 텍스트 <프로바이더> · <모델>  |  ● 비전 <프로바이더> · <모델>`
  - 비전 모델이 설정되지 않았으면 비전 칸은 "비전 사용 안 함"(흐리게). LLM이 설정되지 않았으면 지금처럼 "LLM 설정 안 됨" 한 칸.
- 점: 그 역할로 진행 중인 요청이 하나라도 있으면 초록(#3FB68B), 없으면 회색.
- 화살표(점 다음): 진행 중인 요청 중 하나라도 답을 받는 중이면 ↓(초록 계열), 모두 입력 단계면 ↑(파랑 계열 #4F8EF0), 요청이 없으면 화살표 없음 **[제안: 색]**.
- 역할 칸을 누르면 사용량 팝업이 열린다(어느 칸을 눌러도 같은 팝업).

## 3. 사용량 팝업 [제안, 시안 승인됨]

- 제목 "토큰 사용량", 오른쪽에 "<프로젝트 이름> · 이 프로젝트 누적".
- 표: 작업 / 입력 / 출력 / 합계. 행 순서: 분석, 교정, 화면 확인, 용어집, 번역, 번역 검토, 합계.
  - 각 작업 이름 아래 작은 글씨로 그 작업에 마지막으로 쓴 모델 이름, 쓴 적 없으면 "—".
  - 지금 진행 중인 작업 행에는 초록 점과 "· 진행 중".
  - 서버가 사용량을 알려주지 않은 요청이 있었던 작업에는 이름 아래에 "일부 사용량 정보 없음".
- 아래: "서버가 알려준 사용량 기준 · 생각 토큰은 출력에 포함", [기록 지우기](확인을 거쳐 이 프로젝트의 사용량을 0으로).
- 숫자는 천 단위 구분, 고정폭 숫자.

## 4. 사용량 모으는 규칙 [제안]

- 작업 키: `analyze`(분석), `correct`(교정), `verify`(화면 확인: 교정과 번역 검토에서 부른 것 모두), `glossary`(용어집), `translate`(번역, "이 구간만 번역" 포함), `review`(번역 검토의 일관성 검토).
- 요청 한 번이 끝날 때(성공, 실패 응답, 잘림 모두) 서버 응답의 `usage`에서 입력(`prompt_tokens`)과 출력(`completion_tokens`)을 그 작업에 더한다. 재시도도 각각 더한다(실제로 쓴 양이기 때문).
- 연결 실패나 취소처럼 응답이 없으면 더하지 않는다.
- 프로젝트별로 `project.json`에 저장한다(`tokenUsage`, 없으면 0). 저장 시점: 단계가 끝날 때(성공·실패·취소), 프로젝트를 닫을 때, 앱을 끌 때. 그 사이 앱이 비정상 종료되면 마지막 저장 이후 몫은 잃어도 된다.
- 예전 프로젝트는 0에서 시작한다.

## 5. 입력·출력 구분 [제안]

- 채팅 요청을 스트리밍(`stream: true`, `stream_options: {"include_usage": true}`)으로 보낸다.
- 요청을 보낸 순간부터 첫 응답 조각(본문이든 생각이든)이 올 때까지가 "입력", 그다음부터 끝날 때까지가 "출력"이다.
- 마지막 조각의 `usage`를 사용량으로 쓴다. 없으면 사용량 정보 없음으로 기록한다.
- 스트리밍을 받지 못하는 서버면(400에 `stream`이 거론되면) 그 클라이언트는 기존처럼 한 번에 받는 방식으로 되돌아간다. 이때는 응답이 올 때까지 "입력", 받는 순간 끝으로 본다.
- 기존 동작은 그대로 둔다: 응답 길이 상한, 거절된 필드 빼고 재시도, `finish_reason == "length"`면 잘린 응답, 오류 분류, 취소.
- 제한 시간 300초는 스트리밍에서는 "응답 조각 사이 최대 대기"로 동작한다(URLSession 동작 그대로).

## 6. 함께 하는 것: 자막셋 삭제 [제안, 사용자 응답 대기]

앞 대화에서 제안한 자막셋 삭제는 사용자가 아직 답하지 않았다. 이 계획에는 넣지 않는다.

## 7. 빌더 재량

- 계측 위치(클라이언트 콜백, 감싸는 클라이언트 등), 상태를 앱에 전달하는 방식, 팝업 구현(SwiftUI popover).
- 스트림 파싱 세부(SSE `data:` 줄, `[DONE]`).
